# 车载轨迹数据湖（FastAPI + PyArrow + SQLite）

把车载终端频繁上传的小批轨迹（每批至多 1000 行 CSV）存成不可变 Parquet，
支持“合并现行文件”“按固定清单逐件下载并显式释放”，并能在**两个 API 实例
共享同一卷**时保证：

- 每批原始记录在现行文件集合中恰好出现一次（同一行被上传多次就保留多份）；
- 合并只吃掉“合并开始时快照到的现行文件”，期间新上传的批次不受影响；
- 已领取清单在合并、他方释放、进程崩溃/重启后依然完整可读；
- 旧文件只有在退出所有现行清单与所有未释放清单之后才被回收；
- 任何写盘/登记失败或进程退出都不会暴露半份合并结果。

## 快速启动（两个实例 + 共享卷）

```bash
docker compose up --build
```

- 实例 A：<http://localhost:8080/docs>
- 实例 B：<http://localhost:8081/docs>
- 两个容器都挂载同一个命名卷 `lake-data` 到 `/data`。

在 `/docs` 里可以直接完成演示：`POST /v1/batches` 上传 → `POST /v1/merges`
合并 → `POST /v1/manifests` 领取 → 逐件 `GET .../download` → `POST
.../release` 释放。也可以直接跑黑盒脚本：

```bash
python3 scripts/demo.py --base-url http://localhost:8080 --peer-url http://localhost:8081
```

脚本会在两个实例上并发上传/合并/领取/下载/释放，并校验本轮每条记录恰好出现一次、
旧清单逐件可下载且哈希一致、释放后旧件被回收；退出码非 0 表示不变量被破坏。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/v1/batches` | multipart：`batch_id` + `file`（CSV）。单批 ≤1000 行，批号全局唯一，重复批号返回 409 |
| GET | `/v1/files` | 当前现行文件清单（按登记顺序） |
| POST | `/v1/merges` | 把**开始时**的现行文件合并为一件 |
| POST | `/v1/manifests` | 领取固定文件清单，可选 JSON `{"label": "..."}` |
| GET | `/v1/manifests/{id}` | 查看清单（含每件 sha256/行数/下载地址） |
| GET | `/v1/manifests/{id}/files/{file_id}/download` | 按清单下载 Parquet；清单已释放返回 410 |
| POST | `/v1/manifests/{id}/release` | 显式释放，幂等 |
| GET | `/v1/stats` | 计数（现行/已退/已回收文件、清单数） |
| GET | `/healthz` | 存活探针 |

CSV 约定：UTF-8、带表头，必需列为车辆号、UTC 时刻、纬度、经度。列名支持常见
别名（`vehicle_id`/`device_id`/`车辆号`，`timestamp`/`time`/`时刻`，
`latitude`/`lat`，`longitude`/`lon`/`lng`）。时刻必须是带时区的 ISO 8601
（`Z` 或偏移均可，统一转 UTC 存储），纬度 ∈ [-90, 90]，经度 ∈ [-180, 180]。
重复行不会被去重。

## 一致性设计

**不可变文件 + SQLite 登记表。** 所有 Parquet 一旦发布就不再修改；文件内容先写入
`/data/tmp`，`fsync` 后 `rename` 进 `/data/batches`（POSIX 原子），再在 SQLite
事务里登记。登记提交之前，任何接口都看不到这个文件。

**合并提交是一个事务。** `POST /v1/merges`：

1. 在 WAL 快照里读取现行文件集合（本次合并的输入快照）；
2. 在跨实例的 `flock` 合并锁下把输入拼接写出一件新 Parquet（行序按登记顺序，
   不去重）；
3. 用 `BEGIN IMMEDIATE` 事务同时：插入新文件、写入合并输入明细、把每个输入行
   `UPDATE ... SET live = 0 ... WHERE id = ? AND live = 1`。只要任一输入不再是
   现行（被另一次合并吃掉），整笔事务回滚、输出文件删除并重试；
4. 提交成功才是新文件清单可见的唯一时刻。提交前崩溃只会留下一个未登记的
   Parquet，由孤儿清扫回收。

**领取清单也是一个事务。** 领取时在同一个 `BEGIN IMMEDIATE` 里把当前现行文件
逐件写入 `manifest_files`，因此每份清单都是某个串行时刻的完整切分；两个实例并发
领取/合并时，清单要么看到合并前、要么看到合并后，不会出现半份。

**下载用已打开的文件描述符。** 下载先确认清单仍为 `open`，再 `os.open` 文件，
之后才交给流式响应。即使此刻另一作业释放并触发回收，POSIX 仍允许通过已打开的
描述符读完整个文件。

**旧件回收。** 文件被合并退休（`live=0`）后，只有在
“没有任何 `state='open'` 的清单引用它”时才会把 `recycled_at` 置位并删除磁盘
文件。已释放清单不再钉住文件；未释放清单永不自动过期，所以作业领取后多久回来
都还能读完原清单。释放接口会立即触发一次回收，后台维护线程也会周期性补做。

**崩溃恢复。** SQLite 使用 WAL + `synchronous=FULL`；登记失败会删除刚落盘的
Parquet；进程退出不会留下半份合并结果。重启后维护线程清理未登记文件与残留临时
文件（孤儿有宽限期，且清扫与合并互斥，不会误删刚发布尚未登记的输出）。

## 并发与一致性保证

- SQLite 是唯一的元数据真相来源，写操作全部 `BEGIN IMMEDIATE`；
- 读取使用 WAL 快照，跨实例可见；
- 合并锁仅用于避免重复做功，正确性不依赖它：提交事务会重新校验每个输入的
  `live=1`；
- 两个实例同时首次启动时，WAL 切换与建表都有重试，已在测试中覆盖；
- 单批行数、上传字节数与合并输入行数都有校验，合并输出行数必须等于输入行数之和。

## 测试

```bash
python3 -m pytest tests -q
```

覆盖：

- 重复行在单批、跨批与多次合并后保留原重数；
- 合并只替换快照，合并期间新增批次不丢失；
- 领取清单在合并、其他清单释放、模拟重启后仍逐件可读且哈希一致；
- 同一条记录在并发领取/合并/上传下恰好出现一次；
- 旧文件只有在所有未释放清单都释放后才被回收；
- 未登记的“半份合并输出”不可见，并在宽限期后被清扫；
- 合并提交前崩溃、提交事务中途崩溃：旧清单不变、可重试、无半份结果；
- 登记失败会删除已写出的 Parquet；
- 两个实例并发启动同一卷；
- `/docs`、OpenAPI、上传/合并/领取/下载/释放全链路与错误码。

`scripts/demo.py` 是对真实运行进程的黑盒端到端检查（已在两个进程共享一个目录的
环境下实测通过）。

## 配置

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `LAKE_ROOT` | `/data` | 共享数据根目录（Parquet + SQLite + 锁） |
| `LAKE_MAX_BATCH_ROWS` | `1000` | 单批行数上限 |
| `LAKE_MAX_UPLOAD_BYTES` | `16777216` | 单次上传字节上限 |
| `LAKE_ORPHAN_GRACE_S` | `300` | 未登记文件的孤儿宽限期 |
| `LAKE_MERGE_LOCK_TIMEOUT_S` | `120` | 等待跨实例合并锁的时长 |
| `LAKE_MAINTENANCE_INTERVAL_S` | `30` | 后台回收/清扫周期 |
| `LAKE_DB_BUSY_TIMEOUT_MS` | `30000` | SQLite 锁等待 |

## 已知边界（诚实说明）

- 共享卷需支持 POSIX 语义（`rename`、`flock`、WAL）；在 NFS 等网络文件系统上
  未验证，也不推荐。
- SQLite 单写者：高频合并时写入会串行化；读取不受影响。合并本质上复制数据，
  数据量远大于“小批轨迹”时应换成分区/增量合并策略。
- 未实现鉴权、限流、跨卷复制与历史版本查询；批号重复由调用方负责语义。
- 未释放清单永远不会自动过期，属于有意设计；长期不释放的作业会推迟旧件回收。
- Docker Compose 在本开发沙箱内无法实际启动（无 Docker 守护进程），因此镜像与
  Compose 文件做了静态校验，端到端验证使用两个真实 uvicorn 进程共享同一目录完成。
